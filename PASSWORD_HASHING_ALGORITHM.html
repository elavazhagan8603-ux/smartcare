PASSWORD HASHING ALGORITHM
Secure Login System Using SHA-256 with Salt
Link: [ https://elavazhagan8603-ux.github.io/smartcare/ ]

1. Introduction

This login system demonstrates password hashing with a unique random salt using the SHA-256 hash function. The browser's Web Crypto API performs the hashing. Instead of saving the original password, the system stores only the salt and the resulting hash, so the real password is never kept in the database.

2. Algorithm Used

Algorithm: SHA-256 (Secure Hash Algorithm, 256-bit) applied to salt + password.
Salt length: 16 bytes (128 bits), generated randomly for each account.
Hash output length: 256 bits (32 bytes), stored as a 64-character hexadecimal string.

SHA-256 is a one-way function: the hash can be calculated from the password, but the password cannot be recovered from the hash. Because plain SHA-256 is very fast, production systems prefer slower algorithms such as PBKDF2, bcrypt or Argon2. SHA-256 with salt is used here to explain the core idea clearly. It is a standard algorithm and not a newly invented one.

3. What Is a Salt?

A salt is a random value added to the password before hashing. The salt is not secret and is stored next to the hash. Because every user gets a different salt, two users with the same password get different hashes. This prevents attackers from spotting identical passwords in a leaked database and protects against precomputed hash tables (rainbow tables).

4. Registration Algorithm

  1. Read the username and password entered by the user.
  2. Check that both fields are filled and the password has at least 6 characters.
  3. Check that the username does not already exist.
  4. Generate a secure random 16-byte salt using crypto.getRandomValues().
  5. Join the salt and the password and convert them to bytes using TextEncoder.
  6. Calculate the hash using crypto.subtle.digest("SHA-256", data).
  7. Convert the salt and the hash to hexadecimal strings.
  8. Store the username, salt and hash in the database / localStorage. The password itself is not stored.

5. Login Verification Algorithm

  1. Read the entered username and password.
  2. Retrieve the stored record for the username; if none exists, reject the login.
  3. Take the saved salt from the record.
  4. Join the saved salt with the entered password and hash it with SHA-256.
  5. Compare the new hash with the stored hash.
  6. If both match, show a successful login message; otherwise show "Wrong password".

6. Simplified Pseudocode

REGISTRATION(username, password): salt = SECURE_RANDOM_BYTES(16) hash = SHA256(salt + password) SAVE(username, salt, hash) // Never save the original password LOGIN(username, entered_password): record = LOAD(username) IF record does not exist: RETURN "User not found" candidate_hash = SHA256(record.salt + entered_password) IF candidate_hash == record.hash: RETURN "Login successful" ELSE: RETURN "Wrong password"

7. Important JavaScript Web Crypto Functions

  • crypto.getRandomValues() — Generates the random salt using the browser's secure random number generator.
  • crypto.subtle.digest() — Calculates the SHA-256 hash of the salt and password.
  • TextEncoder() — Converts the text (salt + password) into bytes before hashing.
  • localStorage / Supabase Cloud DB — Stores the account records (username, salt, hash) in the browser and cloud store.

8. Security Notes and Limitations

  • This project is for learning and demonstration. Client-side storage can be inspected by the user, so real credentials must be verified on a trusted backend.
  • A client-side login check can be bypassed. A real application must verify credentials on a trusted backend server over HTTPS.
  • Plain SHA-256 is fast, which helps attackers who try many guesses. Real systems should use bcrypt, PBKDF2 or Argon2id with many iterations.
  • The salt does not need to be secret, but the hash should not be exposed unnecessarily.
  • A production system should also use rate limiting, generic error messages, secure session cookies and safe password-reset options.

9. Conclusion

The login system uses SHA-256 with a unique 16-byte random salt. During registration, the salt and the hash are saved instead of the original password. During login, the entered password is combined with the stored salt, hashed, and compared with the stored hash. This shows the core principle of salted password hashing, while a production system would add a slower algorithm and server-side verification.
